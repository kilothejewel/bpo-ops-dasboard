# BPO Weekly Operations Dashboard

A self-hosted, medallion-architecture data platform and operational dashboard built for a Business Process Outsourcing (BPO) environment. This project demonstrates a production-grade data engineering pipeline and executive reporting layer, serving as Stage 2 of a technical interview/architecture exercise (mapping to an enterprise Azure target state).

---

## 🏛️ Medallion Architecture

The data pipeline strictly adheres to the **Medallion Architecture (Bronze → Silver → Gold → Serving)**:

```
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│  Bronze (Raw)   │ ────> │ Silver (Staging)│ ────> │   Gold (Marts)  │ ────> │  Serving Layer  │
│                 │       │                 │       │                 │       │                 │
│ Python Data Gen │       │  dbt Staging    │       │ dbt Star Schema │       │   Next.js App   │
│ Postgres 'raw'  │       │ Type Cleaned &  │       │ Fact & Dims +   │       │ PostgreSQL      │
│ Schema          │       │ Deduplicated    │       │ Campaign        │       │ 'public_marts'  │
│                 │       │                 │       │ Targets Joined  │       │ Typed Access    │
└─────────────────┘       └─────────────────┘       └─────────────────┘       └─────────────────┘
```

| Layer | Component | Description & Storage Location |
|---|---|---|
| **Bronze (Raw)** | `scripts/generate_data.py` | Untransformed synthetic operational data generated by Python, loaded directly into PostgreSQL `raw` schema (`raw.raw_interactions`, `raw.raw_campaigns`, `raw.raw_agents`, `raw.raw_channels`, `raw.raw_campaign_targets`). |
| **Silver (Staging)** | dbt Staging Models | Canonical schema normalization, deduplication (window functions over `interaction_id`), data type casting, and timestamp difference computations (`stg_interactions`, `stg_campaigns`, `stg_agents`, `stg_channels`, `stg_campaign_targets`). |
| **Gold (Marts)** | dbt Star Schema | Production reporting models (`fct_interactions`, `dim_campaign`, `dim_agent`, `dim_channel`, `dim_date`, `campaign_targets`, `weekly_campaign_kpis`). Aggregates weekly KPIs by dynamically joining `campaign_targets`. |
| **Serving** | Next.js 16 Dashboard | Executive dashboard querying `public_marts` via a typed server-side Data Access Layer (`lib/data-access.ts`) featuring server-side RBAC with signed session cookies, paginated/sortable interaction logs, data-driven Recharts SLA trend and channel-volume charts (with hover tooltips), and a live campaign target health matrix. |

## 📊 Confirmed KPIs & Calculation Rules

All metrics are calculated strictly according to confirmed business specifications:

| Metric Name | Target / SLA | Calculation Logic | Notes |
|---|---|---|---|
| **Calls Answered <1 Min** | **90%** | `(Calls answered within <=60s / Total Phone Calls Evaluated) * 100` | Applies strictly to **Phone** channel. |
| **CSAT Score (Top-Box)** | **45%** | `(CSAT Ratings 4 & 5 / Total Rated Interactions) * 100` | Real, confirmed baseline figure (~45%). |
| **Email First Reply Time** | *No SLA* | `AVG(first_response_at - opened_at)` in minutes | Reported as average in minutes. |
| **Email Resolution Time** | *No SLA* | `AVG(resolved_at - opened_at)` in minutes | Reported as average in minutes. |
| **Volume Counts** | *No Target* | `COUNT(interaction_id)` per channel (Phone, Email, Ticket, Chat) | Trend/count breakdown over time. |

> [!IMPORTANT]
> **Dynamic Target Joining & Boundary Correctness:**  
> SLA adherence is calculated dynamically in dbt (`weekly_campaign_kpis.sql`) by joining `fct_interactions` with `campaign_targets` on `campaign_id` and `metric_name`. **No SLA thresholds are hardcoded in application or dbt SQL code.** Changing a campaign target only requires updating a target record in the database, never a code change.
> 
> Furthermore, metrics are computed and rounded once within a dedicated CTE (`weekly_pct`) before comparison, ensuring displayed values and threshold flags (`is_phone_sla_met`) never diverge at decimal boundaries. If a campaign lacks a target definition for a metric, the SLA status explicitly evaluates to `NULL` rather than a false failure (`0`), allowing the UI to accurately render "No Target Set".

## 🔒 Access Model & Role-Based Security (RBAC)

Security is implemented with defense-in-depth across session issuance (`lib/session.ts`, `app/api/session/route.ts`), the API route (`app/api/dashboard/route.ts`), and the typed Data Access Layer (`lib/data-access.ts`):

- **Signed Session, Not Client-Editable Params**: Identity resolves to one of a small set of named demo personas (`lib/auth-constants.ts` — an Operations Director with management access, plus per-campaign leads with standard access). Once a persona is selected via `POST /api/session`, the server issues an HMAC-signed, `httpOnly` session cookie (`bpo_session`). `GET /api/dashboard` reads role/campaignId **only** from that verified cookie — never from query params — so a client can no longer escalate access by hand-editing a URL.
- **Fail-Closed Principle**: A missing, malformed, expired, or tampered session token is rejected outright (`401 Not authenticated`) rather than defaulting to any role. On every verification, the session is also re-resolved against the current persona table rather than trusting the token's embedded claims verbatim, so a persona removed server-side can't keep granting access via an old token.
- **Server-Enforced Query Shaping**:
  - **Management Role (`management`)**: Full cross-campaign visibility with optional single-campaign drill-down.
  - **Standard Role (`standard`)**: Restricted server-side query execution enforcing `WHERE campaign_id = $1` pinned strictly to the session's `campaignId`. Client-requested campaign IDs are ignored entirely for this role (see `getEnforcedCampaignFilter` in `lib/data-access.ts`).
- **SQL Injection Defense & Input Validation**: Every query is fully parameterized (`$1`, `$2`, ...). `campaignId` and `channel` query params are additionally checked against an allowlist/pattern before use, so malformed input returns a clear `400` instead of a silent empty result. Internal database error messages are never returned to the client — errors are logged server-side and a generic message is returned.

> [!NOTE]
> **Honest limitation**: `POST /api/session` does not verify any real credentials — it issues a session for whichever persona ID is requested, with no password or login step. That's an intentional simplification for a demo project with no user-management system. What it *does* fix is the specific vulnerability this review originally flagged: role/campaignId are no longer trusted directly from a client-editable query string. In a production deployment (per the Azure mapping below), this endpoint would sit behind real authentication — Azure AD (Microsoft Entra ID) SSO — and role/campaignId would be derived from verified AD claims, never from an unauthenticated request body.

## ☁️ Azure Production Target Architecture Mapping

While this Stage 2 exercise is implemented using a self-hosted stack (PostgreSQL + dbt-postgres + Next.js), it directly maps 1:1 to the Stage 1 production Azure design:

| Local Self-Hosted Stack | Production Azure Architecture | Rationale & Trade-offs |
|---|---|---|
| **Python Generator (`generate_data.py`)** | **Azure Data Factory / Microsoft Fabric Pipelines** | Scheduled batch ingestion pipeline landing raw extracts into Azure Data Lake Storage Gen2. Includes deterministic seeding (`Faker.seed(42)`, `random.seed(42)`). |
| **PostgreSQL `raw` Schema** | **Azure Data Lake Storage Gen2 (ADLS Gen2 Bronze)** | Schema-on-read raw landing zone in parquet/JSON format. |
| **dbt Staging Models (`staging`)** | **Synapse Analytics / Fabric Lakehouse (Silver)** | Standardized conformed silver tables with deduplication and staging schema tests (`models/staging/schema.yml`). |
| **dbt Marts Star Schema (`marts`)** | **Synapse Analytics / Fabric Lakehouse (Gold)** | Star schema optimized for analytical query performance and dimensional modeling (`models/marts/schema.yml`). |
| **PostgreSQL `campaign_targets`** | **Azure SQL Database / Fabric Metadata Table** | Dynamic threshold repository for SLA calculations with composite uniqueness constraints. |
| **Next.js signed session cookie (`lib/session.ts`)** | **Azure AD (Microsoft Entra ID) SSO** | Demo persona-based session issuance stands in for a real identity provider; production would derive role/campaignId from verified AD claims, not a request body. |
| **Next.js Server API (`lib/data-access.ts`)** | **Power BI + Azure AD Row-Level Security (RLS)** | Server-side query shaping using session claims, mapping to Azure SQL RLS predicates (`SESSION_CONTEXT`). |
| **Local Connection Config** | **Azure Key Vault & Managed Identities** | Local fallback credentials (`postgres`/`postgres`) are dev-only conveniences; production uses Azure Key Vault and Managed Identity (MSI). |

## 📌 Explicit Assumptions

1. **CSAT Measurement**: CSAT top-box percentage measures satisfied customer responses (ratings 4 and 5 out of 5) relative to total survey responses.
2. **Channel Scope for Phone SLA**: Phone SLA adherence measures calls answered within 60 seconds of `opened_at` timestamp.
3. **Weekly Cadence**: Data is aggregated with weekly granularity (ISO week number and week start date), matching the BPO operational review cycle.
4. **Data Quality Edge Cases**: Synthetic generator deliberately includes duplicates (deduplicated in `stg_interactions`), nulls (unresolved/unrated tickets), and late-arriving records to validate dbt `unique`, `not_null`, and `relationships` data quality tests.

## 🔑 Environment Variables

All configuration is read from environment variables. Every variable has a **dev-only default**, so a stock local setup (Postgres superuser `postgres`/`postgres` on `localhost:5432`) runs with no configuration at all. A template lives in [`.env.example`](.env.example).

| Variable | Used by | Default (dev only) | Required in prod? | Purpose |
|---|---|---|---|---|
| `POSTGRES_HOST` | generator, dbt, dashboard | `localhost` | Yes | Database host |
| `POSTGRES_PORT` | generator, dbt, dashboard | `5432` | No | Database port |
| `POSTGRES_DB` | generator, dbt, dashboard | `bpo_db` | Yes | Database name |
| `POSTGRES_USER` | generator, dbt, dashboard | `postgres` | Yes | Database user (use a read-only role for the dashboard in prod) |
| `POSTGRES_PASSWORD` | generator, dbt, dashboard | `postgres` | **Yes — secret** | Database password |
| `SESSION_SECRET` | dashboard (`lib/session.ts`) | public placeholder string | **Yes — secret** | HMAC key that signs the `bpo_session` cookie. Anyone who knows it can forge a session, so the fallback must never reach a shared environment. Generate with `openssl rand -base64 32`. |
| `DBT_TARGET_DIR` | dashboard (`lib/dbt-status.ts`) | `../dbt_bpo/target` | Only if relocated | Where to find dbt's `run_results.json` for the live "dbt tests: N/N passing" badge and dbt version. Set it when the dashboard runs outside the repo checkout (e.g. a container with the artifacts mounted). |
| `NODE_ENV` | dashboard | set by Next.js | Set automatically | `production` enables the cookie `Secure` flag and disables the dev-mode pg pool cache. Don't set it by hand. |

**Where each component reads them from:**

- **Dashboard (Next.js)** loads `dashboard/.env.local` automatically: `cp .env.example dashboard/.env.local`.
- **Python generator and dbt** read from the shell environment. Copy `.env.example` to `.env`, then `set -a; source .env; set +a` before running `generate_data.py` or `dbt`. `dbt_bpo/profiles.yml` resolves the same `POSTGRES_*` names through `env_var()`.
- **Production (Azure)**: these become Key Vault secrets surfaced as App Service / Container Apps settings; with Managed Identity the `POSTGRES_PASSWORD` entry goes away entirely (see the mapping table above).

`.env`, `.env.local` and `*.env` are git-ignored; only `.env.example` (which holds no real secrets) is committed.

## 🚀 Step-by-Step Setup & Verification Guide

### Prerequisites
- Python 3.10+
- PostgreSQL 12+
- Node.js 18+ and npm
- `dbt-postgres` adapter

### 1. Database Setup
Create PostgreSQL database `bpo_db`:
```bash
psql -U postgres -c "CREATE DATABASE bpo_db;"
```

### 2. Generate Synthetic Dataset & Load Bronze Layer
Install Python dependencies and execute the dataset generator:
```bash
pip install pandas faker psycopg2-binary
python scripts/generate_data.py
```
*Output*: Generates ~3,600 realistic interaction records across 4 campaigns and loads them into PostgreSQL `raw` schema.

### 3. Run dbt Transformations & Data Quality Tests
Navigate to `dbt_bpo/` and execute dbt:
```bash
cd dbt_bpo
dbt deps --profiles-dir .
dbt run --profiles-dir .
dbt test --profiles-dir .
```
*Verification*: Confirms 12 dbt models created in `public_staging` and `public_marts` schemas, and comprehensive data quality tests passing across both silver staging (asserting deduplication and channel normalization) and gold marts (referential integrity, dynamic target constraints, metric ranges, and a singular reconciliation test).

### 4. Manual SLA Calculation Verification
Reconcile SLA output between raw data and dbt marts output:
```sql
SELECT 
    'RAW' as source,
    COUNT(CASE WHEN channel='phone' THEN 1 END) as total_phone_calls,
    SUM(CASE WHEN channel='phone' AND EXTRACT(EPOCH FROM (first_response_at - opened_at)) <= 60 THEN 1 ELSE 0 END) as calls_under_60s,
    ROUND((SUM(CASE WHEN channel='phone' AND EXTRACT(EPOCH FROM (first_response_at - opened_at)) <= 60 THEN 1 ELSE 0 END)::numeric / NULLIF(COUNT(CASE WHEN channel='phone' THEN 1 END), 0)) * 100, 2) as call_sla_pct
FROM raw.raw_interactions
WHERE campaign_id = 'CMP-101'

UNION ALL

SELECT 
    'DBT_MARTS' as source,
    SUM(call_volume) as total_phone_calls,
    SUM(calls_answered_under_1min_count) as calls_under_60s,
    ROUND((SUM(calls_answered_under_1min_count)::numeric / NULLIF(SUM(total_calls_evaluated), 0)) * 100, 2) as call_sla_pct
FROM public_marts.weekly_campaign_kpis
WHERE campaign_id = 'CMP-101';
```

This is also automated as a dbt singular test — see `dbt_bpo/tests/assert_phone_sla_reconciles.sql`, which runs on every `dbt test`.

### 5. Launch Dashboard Application
Navigate to `dashboard/` and start Next.js dev server:
```bash
cd dashboard
npm install
npm run dev
```
Open [http://localhost:3000](http://localhost:3000) in your browser. The dashboard establishes an initial demo session automatically (Operations Director persona) — use the tier switcher to try other personas.
